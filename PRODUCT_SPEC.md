## Текущий frontend-MVP

### Бренд и задача

KARMA — магазин кастомных акриловых ночников и настенных световых панелей.

Пользователь должен почувствовать, что это не дешевый массовый товар, а стильная вещь для атмосферы комнаты: любимый персонаж, игра, фильм, автомобиль или собственный дизайн.

### Стиль интерфейса

- Основной фон: глубокий черный и графитовый.
- Неоновые акценты: фиолетовый, синий, бирюзовый и немного розового.
- Эффект мягкого свечения у карточек и кнопок.
- Атмосферный фон с размытыми световыми пятнами.
- Glassmorphism использовать умеренно.
- Футуристичный, но читаемый русский интерфейс.
- Приложение в первую очередь должно красиво работать на мобильном экране Telegram.
- Кнопки должны иметь приятную tap-анимацию.
- Переходы между экранами должны быть плавными.
- Корзина должна красиво показывать количество товаров.
- Не использовать перегруженный киберпанк, кислотные цвета и нечитаемые декоративные шрифты.
- Дизайн должен быть премиальным и удобным.

## Будущая структура базы данных

### Настройки магазина

- `StoreSettings` хранит название магазина, подзаголовок, hero-заголовок, hero-подзаголовок, логотип, hero-изображение, контактный текст и текст доставки.
- Логотип и hero-изображение должны редактироваться через будущую админку.
- На старте предполагается одна активная запись настроек магазина.

### Каталог

- `Category` хранит категории каталога: название, slug, обложку, порядок сортировки и активность.
- `Subcategory` хранит подкатегории и связана с `Category`.
- `Product` хранит товар, его подкатегорию, slug, описание, тип товара, флаги `isFeatured` и `isActive`.
- Категория товара определяется через связь `Product -> Subcategory -> Category`, чтобы не допустить рассинхрона категории и подкатегории.
- `ProductImage` хранит обложку и галерею товара: URL, storage path, alt-текст, признак обложки и порядок.
- У одного товара может быть только одно изображение с `isCover = true`; это правило должно быть защищено PostgreSQL partial unique index в миграции.
- `ProductVariant` хранит варианты изделия: тип изделия, размер в сантиметрах и цену в копейках.
- Комбинация `productId + itemType + sizeCm` должна быть уникальной.
- Тестовые цены в frontend и seed должны использовать одну матрицу цен в копейках.

### Пользователи и заказы

- `TelegramUser` подготавливает будущую Telegram-интеграцию и хранит Telegram ID, username, имя, фамилию и телефон.
- `Order` хранит заказ, публичный номер, контактные данные, Telegram-данные при наличии, комментарий, итог в копейках, статус оплаты, статус обработки и согласие на обработку данных.
- `DeliveryAddress` хранит адрес, сохраненный именно для конкретного заказа.
- `OrderItem` хранит позиции заказа.
- Заказ должен сохранять исторический снимок товара, изображения, типа изделия, размера и цены на момент покупки, даже если позже товар или цена изменятся в админке.

### Оплата и уведомления

- `Payment` подготавливает будущие интеграции ЮKassa или Т-Банк: провайдер, ID платежа у провайдера, сумма, статус, idempotency key, confirmation URL и raw webhook payload.
- `NotificationLog` нужен для защиты от дублирующихся Telegram-уведомлений администраторам.

### Изображения

- Публичные изображения каталога должны храниться в Supabase Storage bucket `catalog-images`.
- Изображения магазина, hero, логотипа и товаров должны храниться в public bucket `catalog-images`.
- Изображения, которые клиент загрузит для кастомного заказа, должны храниться отдельно в private bucket `custom-order-uploads`.
- Загрузка и удаление публичных изображений из админки должны выполняться только через защищенный серверный код администратора.
- `SUPABASE_SECRET_KEY` нельзя передавать во frontend.
- На текущем этапе используются только локальные mock-ассеты, реальные загрузки через админку будут подключены позже.
## Реализованный статус базы данных

- Структура базы данных создана в Supabase через initial Prisma migration.
- Все 12 таблиц приложения существуют, RLS включен, partial unique index для единственной обложки товара создан.
- Тестовый каталог заполнен безопасным seed.
- В базе есть `StoreSettings = 1`, `Category = 4`, `Subcategory = 8`, `Product = 10`, `ProductImage = 30`, `ProductVariant = 90`.
- Цены и варианты изделий находятся в базе в копейках.
- Покупательские данные, заказы, платежи и уведомления seed не создавал.
- Реальные изображения товаров еще не загружены; сейчас используются mock-изображения.
- Следующий этап — подключить клиентский каталог и главную страницу к database repository.
- До подключения repository frontend продолжает работать на mock-данных.
## Текущий статус storefront

- Пользовательский каталог и главная страница переведены на database-backed чтение через server-side repository.
- Категории, подкатегории, товары, изображения, варианты и цены приходят из базы.
- Checkout пока остается demo-сценарием и не создает `Order`.
- Корзина хранит локальный snapshot выбранного варианта товара до этапа реального оформления заказа.
- Mock-файлы и локальные SVG остаются в проекте, потому что seed-изображения пока ссылаются на них.

## Будущий вход администратора через Telegram

- Администратор будет открывать защищенную панель через Telegram Mini App.
- Допуск администратора строится на server-side проверке `Telegram.WebApp.initData`, подписанной ботом.
- Обычный браузер не должен получать доступ к управлению магазином.
- Текущая страница `/admin` является только безопасной заглушкой для проверки доступа.
- Полноценное тестирование admin-допуска будет возможно после публикации приложения по HTTPS URL и подключения Mini App к боту в BotFather.
- Реальные CRUD-операции, загрузка изображений, управление заказами и настройками магазина пока не подключены.

- Управление товарами, категориями, ценами и товарными изображениями остается следующим этапом.

## Прайс-листы в админке

Панель управления получает раздел `Прайс-листы`. На первом этапе администратор может редактировать цену в рублях и note существующих пунктов основного прайса `Основной прайс KARMA`.

Нельзя менять через этот раздел тип изделия, размер, порядок, активность, создавать новые пункты или удалять существующие. Это защищает рабочую матрицу размеров от случайного повреждения.

Будущие разделы админки:

- `Категории` — управление категориями и подкатегориями.
- `Импорт товаров` — массовое добавление метаданных карточек через Excel/CSV после CRUD каталога.

Перед созданием настоящего заказа и перед оплатой сервер должен повторно получить актуальный `PriceListItem.priceKopecks` из базы. Snapshot цены в localStorage нужен для интерфейса корзины, но не должен быть единственным источником суммы оплачиваемого заказа.

## Production-статус раздела прайс-листов

Раздел `Прайс-листы` работает в production внутри защищенной Telegram-админки. Администратор может менять цену и note существующих вариантов основного прайса `Основной прайс KARMA`.

Структура типов изделий и размеров защищена от изменения через интерфейс: нельзя создавать, удалять или менять состав пунктов прайса на этом этапе.

Production live-проверка сохранения прайса пройдена успешно: PATCH был выполнен без намеренного изменения значений, storefront продолжил показывать те же реальные цены, а note для `Настенная панель / 55 см` осталась видимой.

Следующий этап — управление категориями и подкатегориями каталога.

## Раздел админки `Категории`

В защищенной Telegram-админке появляется рабочий раздел `Категории`. Он нужен для текущей структуры каталога и для будущего импорта карточек товаров.

Администратор сможет:

- создавать категории;
- переименовывать категории без изменения slug;
- скрывать и снова показывать категории;
- создавать подкатегории внутри выбранной категории;
- переименовывать подкатегории без изменения slug;
- скрывать и снова показывать подкатегории.

Физическое удаление категорий и подкатегорий пока недоступно. Если в категории или подкатегории есть активные товары, скрытие требует отдельного подтверждения, потому что связанные товары перестанут отображаться в магазине.

Slug создается сервером при создании записи и остается стабильным после переименования. Это готовит каталог к будущему Excel/CSV import: импорт сможет сопоставлять карточки товаров с категориями по стабильным slug/id, а не по изменяемому отображаемому названию.

## Production-статус раздела категорий

Раздел `Категории` работает в production внутри Telegram Mini App. Администратор может создавать подкатегории для будущих товаров, а созданные пустые разделы остаются видимыми в admin UI.

Пустые категории и подкатегории не отображаются покупателям в публичном storefront до тех пор, пока в них не появятся активные товары.

Следующим этапом становится CRUD карточек товара с выбором подкатегории и основного прайса. Excel/CSV import будет использовать уже созданную структуру категорий и подкатегорий.

## Раздел админки `Товары`

Раздел `Товары` становится рабочим CRUD-интерфейсом карточек каталога. Администратор может создать новую карточку, отредактировать название, описание, подкатегорию, тип товара, featured-статус и показ в магазине.

Новая карточка создается скрытой и автоматически получает основной прайс `PriceList main`. Перед публикацией администратор должен загрузить главную обложку через защищенный flow фотографий, проверить карточку и только затем включить показ в магазине.

Форма списка товаров поддерживает поиск, фильтр категории, фильтр подкатегории, фильтр статуса и пагинацию. В карточке редактирования показываются slug, состояние основного прайса, готовность к публикации и встроенный блок управления фотографиями.

Slug товара создается сервером и не меняется после переименования. Физическое удаление товара пока недоступно: неполные или устаревшие карточки скрываются через `isActive = false`.

Массовый Excel/CSV import метаданных товара будет отдельным этапом. Импортированные товары должны использовать тот же безопасный flow: создаваться скрытыми, получать `PriceList main`, а фотографии загружаться отдельно через Telegram-админку.

## Production-статус раздела товаров

Раздел `Товары` работает в production внутри Telegram Mini App. Администратор может создать карточку, добавить главную обложку и опубликовать товар после проверки.

Production-сценарий подтвержден на товаре `Монки Д. Луффи`: карточка была создана скрытой, получила обложку, опубликована в подкатегории `One Piece` и появилась в публичном каталоге.

Опубликованный товар использует общую реальную матрицу цен из `PriceList main`, открывается в карточке товара и может быть добавлен в корзину.

Следующим этапом будет массовый импорт метаданных карточек товара без изображений. Фотографии для импортированных карточек остаются ручной операцией через защищенную админку.

## Раздел админки `Импорт товаров`

На первом этапе импорт товаров работает как preview-only подготовка CSV-файла. База не изменяется: администратор скачивает шаблон, заполняет его в Excel, загружает CSV обратно и видит проверку строк.

Production-база уже поддерживает `Product.externalId` для импортируемых товаров. Существующие ручные товары могут оставаться без `externalId`; стабильный внешний идентификатор нужен для будущих повторяемых импортов.

CSV-шаблон использует UTF-8 с BOM и разделитель `;`. Колонки:

- `external_id` — постоянный идентификатор товара для повторяемого импорта.
- `name` — название товара.
- `description` — описание.
- `category_slug` — slug существующей категории.
- `subcategory_slug` — slug существующей подкатегории внутри категории.
- `product_type` — `REGULAR` или `CUSTOM`, при пустом значении используется `REGULAR`.

CSV не содержит цены, размеры, изображения, `isActive` и `isFeatured`. Новым товарам в будущем автоматически назначается `PriceList main`, а фотографии добавляются отдельно через защищенный раздел `Товары`.

Раздел `Импорт товаров` работает в production в режиме предпросмотра. Production-сценарий CSV подтвержден: две новые строки определены как `CREATE`, конфликт с ручным товаром `Монки Д. Луффи` определен как `ERROR`, каталог не изменен.

Применение импорта и запись товаров в базу остаются отдельной будущей функцией. Будущие импортированные карточки должны создаваться скрытыми, с основным прайсом и без фотографий.

Первая версия применения импорта добавляет кнопку `Создать скрытые товары` только после чистого preview, где все строки имеют действие `CREATE`, а `ERROR` и `UPDATE` равны нулю. Перед созданием администратор подтверждает, что товары будут скрытыми и потребуют ручной загрузки фотографий.

Если в файле есть ошибки или строки `UPDATE`, применение блокируется. Новые товары появляются только в админке: они создаются скрытыми, с `PriceList main`, без фотографий и не отображаются покупателям до ручной публикации.

## Production-status create-only CSV import

Раздел `Импорт товаров` умеет применять чистый CSV для создания новых скрытых карточек товара. Apply доступен только после успешного preview без `ERROR` и `UPDATE`, повторно валидирует исходный CSV на сервере и создаёт товары атомарно.

Production-сценарий подтверждён: импортированы скрытые товары `Ророноа Зоро` и `Донкихот Росиант` (`externalId = anime_onepiece_rosinante_001`; текущее отображаемое имя в production именно такое). Оба товара созданы без фотографий, с `PriceList main`, не опубликованы и не видны покупателям в публичном каталоге.

Товары без фото не публикуются покупателю. Для появления импортированной карточки в магазине администратор должен вручную загрузить cover через раздел `Товары`, проверить карточку и включить показ в магазине.

Следующий крупный блок после стабилизации каталога — покупательский заказ: server-side создание заказа, адрес доставки, Telegram-уведомления, статусы заказа и тестовая оплата.

## Order flow foundation

Покупательский заказ должен создаваться только после server-side quote: сервер заново проверяет товары, активность категорий, `PriceListItem`, цену, тип изделия и размер. Значения из localStorage корзины не являются источником истины для оплаты.

### Pricing rules

- Item subtotal берётся из актуального `PriceListItem.priceKopecks`.
- Snapshot заказа хранит product, `priceListItemId`, тип изделия, размер, цену, note и quantity.
- Custom drawing styles: `CUSTOM_DRAWING_STYLE_1` `+690 ₽`, `CUSTOM_DRAWING_STYLE_2` `+790 ₽`, `CUSTOM_DRAWING_STYLE_3` `+990 ₽`.
- Доплата за custom drawing не участвует в скидке и должна храниться snapshot-ом.
- Скидка на второе изделие: `30%` один раз на самый дешёвый physical unit среди `STANDARD` / `PREMIUM` / `WALL_PANEL`.
- Quantity считается как отдельные eligible единицы; delivery и custom drawing surcharge в скидке не участвуют.

### Delivery

Доставка Почтой России отображается отдельной строкой: `450 ₽`, если в заказе только `STANDARD` / `PREMIUM`; `550 ₽`, если есть хотя бы одна `WALL_PANEL`.

### Custom design order

Пользователь загружает изображение, выбирает стиль отрисовки и ждёт проверки администратором. Статусы review: `PENDING_REVIEW`, `APPROVED`, `REJECTED`. До `APPROVED` custom order не должен автоматически уходить в оплату. Файлы custom order должны храниться отдельно от публичного catalog bucket, в private bucket.

### Customer contact and payment

Заказ должен хранить Telegram ID/username/name, ручной телефон или другой fallback contact, адрес доставки и комментарий. ЮKassa / Т-Банк подключаются только после отдельного согласования доступа; до этого возможен demo/test-payment flow.

### Production order schema status

Production database уже поддерживает order structure для будущего checkout: order/item snapshots, delivery method, delivery address line, discount fields, custom drawing surcharge и custom image review statuses.

Pricing foundation готов: следующий функциональный шаг - quote endpoint и checkout UI, где сервер заново проверяет корзину, цены, доставку, скидку и custom drawing surcharge.

Custom design order с загруженным изображением требует admin image review до оплаты. До `APPROVED` такой заказ не должен попадать в payment flow.

### Server quote

Checkout рассчитывает сумму через `POST /api/orders/quote`. Сервер принимает только `productId`, `priceListItemId`, `quantity`, delivery method и optional custom drawing metadata, а цены, тип изделия, размер и note берёт из базы.

Quote summary показывает строки: товары, отрисовка, скидка, доставка Почтой России и итог. Если товар скрыт, категория скрыта или вариант цены недоступен, checkout показывает безопасную ошибку и не позволяет продолжить.

### Order creation without online payment

Checkout создаёт заказ через `POST /api/orders` только внутри Telegram Mini App. Клиент передаёт cart payload, delivery method, контакт, адрес доставки, комментарий и `X-Telegram-Init-Data`; сервер валидирует Telegram user и заново пересчитывает quote перед записью.

Форма checkout содержит ФИО получателя, телефон, город, индекс, улицу, дом, квартиру, дополнительный контакт и комментарий. Кнопка активна только при успешном quote, заполненных обязательных полях, согласии на обработку данных и доступном Telegram initData.

При успешном создании сохраняются `TelegramUser`, `Order`, `OrderItem` и `DeliveryAddress`. Order snapshot фиксирует товары, `PriceListItem`, тип изделия, размер, note, quantity, цены, скидку, доставку, custom drawing surcharge и итог. `Payment` на этом этапе не создаётся, кнопка оплаты не показывается.

Публичный номер заказа показывается покупателю в формате `KRM-YYYYMMDD-XXXXXX`. Для custom drawing строк item-level review status становится `PENDING_REVIEW`; админские уведомления подключаются отдельным следующим этапом.

Первый production live-заказ без онлайн-оплаты успешно создан под номером `KRM-20260601-128352`. В этом сценарии `Payment` не создаётся, а магазин показывает покупателю номер заказа и сообщение о последующем подтверждении.

Success/error/status сообщения в checkout и админских разделах должны быть заметны сразу после действия: при появлении важного блока интерфейс прокручивает его в видимую область. Это особенно важно внутри Telegram Mini App, где пользователь мог остаться ниже результата действия.

Будущее управление скидками в админке будет отдельным блоком: глобальная скидка и скидки на конкретные товары требуют явных правил приоритета и сохранения snapshot в заказе.

### Telegram admin notifications

После успешного создания заказа без онлайн-оплаты сервер отправляет Telegram-уведомление администраторам.

Уведомление содержит:

- публичный номер заказа;
- состав заказа со snapshot названия товара, типа изделия, размера, количества и цены;
- сумму товаров, скидку, доставку и итог;
- способ доставки и адрес;
- контакт покупателя;
- комментарий покупателя, если он заполнен;
- статусы обработки и оплаты;
- пометку, что онлайн-оплата пока не подключена.

Уведомление отправляется после сохранения заказа. Если Telegram Bot API временно недоступен, созданный заказ остаётся успешным, а попытка отправки логируется для защиты от дублей и будущего аудита.

До подключения платёжного провайдера `Payment` не создаётся. Следующий live-test после deployment должен проверить получение уведомления администраторами на новом тестовом заказе без онлайн-оплаты.

Production live-test Telegram admin notification пройден успешно на заказе `KRM-20260601-805754`. Checkout создал заказ, экран прокрутился к результату, администратор получил уведомление с summary заказа, totals, status-полями и подтверждением, что оплата пока не подключена.

В документации не фиксируются полные персональные данные покупателя: можно подтверждать только наличие recipient/contact/address/comment. `Payment` остаётся future stage.

### Раздел админки `Заказы`

В защищённой Telegram-админке появляется раздел `Заказы`.

Администратор может:

- видеть список заказов с фильтром по статусу, поиском по номеру и пагинацией;
- открыть детальную карточку заказа;
- увидеть состав заказа, snapshot товаров, размеры, цены, скидку, доставку и итог;
- увидеть контакт, адрес доставки и комментарий покупателя внутри защищённого admin UI;
- увидеть payment status как read-only поле;
- изменить fulfillment status заказа по ограниченным переходам.

На этом этапе нельзя менять payment status, суммы, товары, адрес, удалять заказ или создавать `Payment`. Онлайн-оплата и payment-provider integration остаются отдельным будущим этапом.
### Production check: admin order status

Раздел `Заказы` работает в production внутри защищённой Telegram-админки.

Администратор может открыть заказ и сменить fulfillment status по разрешённой state machine. Production-сценарий подтверждён на заказе `KRM-20260601-805754`: статус изменён `NEW -> IN_WORK`, при этом `paymentStatus` остался `PENDING`.

Смена fulfillment status не меняет суммы, состав заказа, адрес доставки, payment status и не создаёт `Payment`. В текущей версии она также не отправляет Telegram notification клиенту или администратору; уведомления о смене статуса проектируются отдельным этапом.
### Customer section: Мои заказы

Покупатель внутри Telegram Mini App может открыть раздел `Мои заказы`.

Список заказов показывает только заказы текущего Telegram user: номер, fulfillment status, payment status, итог, дату и краткий состав. Если заказов нет, показывается спокойное пустое состояние.

Детальная страница заказа `/orders/<publicNumber>` показывает номер, статусы, состав заказа, snapshot цен, скидку, доставку, итог, адрес доставки, контакт и комментарий. Чужие заказы не раскрываются: для них возвращается безопасное состояние `Заказ не найден`.

После успешного checkout покупатель видит кнопку `Открыть заказ`, ведущую на страницу созданного заказа. Страницы заказов read-only: они не создают новые заказы, не меняют статусы и не создают `Payment`.

Кнопка `Связаться` открывает отдельный Telegram support bot `@karmashopsupportbot`, подключённый к CRM BlueSales. Менеджер отвечает покупателю в Telegram через BlueSales, а Mini App не реализует собственный чат.

Ссылка передаёт публичный номер заказа в `start` parameter: для `KRM-20260601-805754` используется `order_KRM_20260601_805754`. На странице показывается текст `Напишите нам по заказу <номер>. Менеджер ответит в Telegram.`

В клиентском UI не используются bot token, admin IDs или server credentials. Username support bot публичный; управление этим значением через StoreSettings можно добавить отдельным будущим этапом.

### FAQ / Как заказать

Покупатель может открыть раздел `/faq` из нижней навигации Mini App.

Раздел объясняет:

- что такое светильники KARMA;
- как оформить заказ;
- размеры и виды: стандарт, премиум, настенная панель;
- заказ по своей картинке;
- стили отрисовки и доплаты: стиль №1 `+690 ₽`, стиль №2 `+790 ₽`, стиль №3 `+990 ₽`;
- требования к изображению;
- доставку Почтой России: `450 ₽` или `550 ₽` при наличии настенной панели;
- как связаться по заказу через support bot.

FAQ-тексты хранятся в `FaqSection` и редактируются через защищённый раздел админки `FAQ / Как заказать`. Текст хранится как plain text / markdown-lite и рендерится безопасно без raw HTML. Если база FAQ пустая, покупатель видит fallback content до заполнения администратором.

Migration `00000000000004_add_faq_sections` уже применена в production. Текущее состояние после применения: `FaqSection = 0`, поэтому fallback остаётся ожидаемым до первого сохранения default sections в админке. Оплата и уведомления клиенту при смене статуса этим этапом не добавляются.

После live-проверки FAQ верхний intro-блок и нижний CTA-блок также редактируются через FAQ-админку. Для них используются reserved slugs `faq-hero-eyebrow`, `faq-hero`, `faq-contact-cta`; эти системные секции не выводятся как обычные раскрывающиеся FAQ-карточки.

Раскрывающиеся FAQ-карточки должны давать понятный визуальный feedback: hover/focus состояние, подсветка открытой карточки и поворот chevron. Это помогает покупателю видеть, какой раздел открыт.

### YooKassa redirect payment creation

Customer order detail can start online payment for eligible orders through YooKassa redirect.

When the buyer presses `Перейти к оплате`, the Mini App calls `POST /api/orders/[publicNumber]/payment/prepare` with Telegram initData. The server verifies that the order belongs to this Telegram user, checks payment eligibility, prepares a YooKassa redirect payment, saves a local `Payment` row after the provider response, and returns `confirmationUrl`.

Regular pending orders can be paid immediately. Custom orders can be paid only after all uploaded images are approved by an administrator. Pending review and rejected custom images keep payment blocked with a clear customer message.

The first version does not include webhook handling. A redirect/confirmation URL does not mark the order as paid by itself; final `PAID` status must be handled by a future webhook or provider status check. Existing pending YooKassa payments with confirmation URL are reused to avoid duplicates.

Real YooKassa payment creation is behind the explicit server flag `YOOKASSA_PAYMENTS_ENABLED=true`. If shop id, secret key and return URL exist but the flag is absent or false, the customer still sees the safe disabled payment guidance and no provider request is made.

### YooKassa receipt payload

The current YooKassa shop requires a fiscal receipt in payment creation requests.

The receipt is generated server-side from the saved order snapshot:

- physical order items become `commodity` receipt items;
- custom drawing surcharge becomes a separate `service` item when present;
- delivery becomes a separate `service` item when present;
- item descriptions are plain text and trimmed to provider-safe length;
- VAT code is read from `YOOKASSA_VAT_CODE` with documented default `1` only when the env value is absent;
- receipt customer uses order phone or email, and payment preparation is blocked before the provider call if neither is available.

Discounts are not sent as a negative receipt line. They are allocated into commodity item amounts so the sum of receipt items equals `Order.totalKopecks`.

The next live payment retry must keep `YOOKASSA_PAYMENTS_ENABLED=false` until the explicit controlled test step, then enable it only for the test window.

### YooKassa webhook foundation

The payment finalization layer is prepared as `POST /api/yookassa/webhook`.

The endpoint is server-to-server and does not use Telegram initData. It is protected by `YOOKASSA_WEBHOOK_SECRET`, passed as a query token or internal header. The production URL pattern for the YooKassa cabinet is:

`https://karma-miniapp.vercel.app/api/yookassa/webhook?token=<secret>`

Supported events:

- `payment.succeeded`: finds an existing YooKassa `Payment`, validates amount and order metadata, updates `Payment.status = PAID`, then updates `Order.paymentStatus = PAID`;
- `payment.canceled`: finds an existing YooKassa `Payment`, validates amount and order metadata, updates `Payment.status = CANCELLED`, and does not mark the order paid.

The webhook does not create orders, does not create payment rows, does not change fulfillment status, totals, items, customer data or images. Unknown events and validation mismatches are ignored safely so provider retries do not corrupt the order state.

Webhook registration in YooKassa and live webhook testing remain separate future steps.
